# Native AI Core — Glossary

Domain terms used across ai-native-core contracts, docs, and adapters.

---

## A

**ADD (Agent-Driven Development)**
Software development methodology where AI agents are primary actors in the development lifecycle. Humans shift from "writing code" to "describing intent and reviewing results."

**Adapter**
Implementation that binds a runtime or product to abstract core contracts. Example: `ai-native-skills` adapts skill contracts; a Hermes profile adapts runtime contracts.

**AGENTS.md**
Project-level agent context file. Gives agents persistent, project-specific knowledge (build commands, code style, architecture constraints, prohibitions). Runtime-agnostic name for CLAUDE.md, .cursorrules, etc.

**Agent Layer** (Layer 7)
Architecture layer defining specialized agent roles and their boundaries. Agents execute assigned responsibilities — they don't own the system.

## B

**Blueprint Layer** (Layer 2)
Architecture layer that turns intent into structured product and system design. Outputs: domain model, bounded context, API contract, system diagram.

**Bounded Context**
DDD concept — a boundary within which a domain model is consistent. Different bounded contexts may use different models for the same real-world concept.

## C

**Capability**
What a skill contract declares an agent can do. A single atomic function (e.g., `systematic_root_cause_debugging`).

**Conformance**
Degree to which an adapter skill covers a contract's quality gates, outputs, and inputs. Validated by `validate-conformance.py`.

**Context Engineering**
The discipline of providing agents with the right information at the right time. Supersedes "prompt engineering." Involves: task descriptions, examples, RAG, tool definitions, state/history, compaction.

**Contract**
A YAML specification defining what must be true about a capability, workflow, or runtime component. Contracts define the "what" — adapters define the "how."

**Contract Version**
Semver version pinned by adapters (e.g., `^2.0.0`). Prevents silent drift when core contracts change.

**Core**
The `ai-native-core` repository. Public, runtime-agnostic contract layer. Contains contracts, docs, ports, architecture, glossary.

## D

**Development Loop**
The canonical execution cycle: Explore → Plan → Implement → Verify → Review → Document → Deliver. Formalized in `development-loop.contract.yaml`.

**Do-Not Section**
Required section in AGENTS.md listing explicit prohibitions. Must have ≥ 3 enforceable items.

## E

**Engineering Contract Layer** (Layer 3)
Architecture layer that locks technical decisions: architecture style, stack, folder conventions, API conventions, testing rules, security baseline.

**Evaluation Layer** (Layer 11)
Architecture layer defining quality gates: architecture compliance, security, performance, maintainability, user value.

**Exit Gate**
Condition that must be met before an agent can proceed to the next phase. Example: "all tests pass with evidence."

## G

**Gate (Quality Gate)**
An enforceable constraint in a contract. Agents must satisfy gates to claim conformance. Example: `verify_phase_must_use_real_tool_output_not_claims`.

## H

**Hook**
Deterministic script that runs at a specific lifecycle point (pre-commit, post-edit). Unlike advisory rules, hooks guarantee execution.

## I

**Implements**
Frontmatter field in adapter skills declaring which core contract they satisfy. Example: `ai-native-skills.implements: ai-native-core/contracts/skills/engineering/master-engineer.contract.yaml`.

**Intent Layer** (Layer 1)
Architecture layer defining why a product or feature exists. Outputs: problem statement, success metric, non-goals.

## K

**Knowledge Layer** (Layer 4)
Architecture layer storing explicit source-of-truth knowledge: product knowledge, domain knowledge, business rules, design rules, technical references.

## L

**Loop Layer** (Layer 10)
Architecture layer defining execution flow. See Development Loop.

## M

**Manifest**
Auto-generated registry (`contracts/manifest.yaml`) listing all contracts with paths, versions, and checksums. Regenerated by `generate-manifest.sh`.

**Memory Layer** (Layer 9)
Architecture layer for decision history and learning. Memory should point back to source-of-truth artifacts, not replace documentation.

**Memory Types**
Four types: session (within conversation), persistent (cross-session files), episodic (past session recall), procedural (skills — reusable approaches).

**Meta-Skill**
Skill type that orchestrates other skills dynamically based on intent detection. Examples: `role-switcher`, `workflow-router`.

**MCP (Model Context Protocol)**
Anthropic's standardized tool integration protocol. Allows agents to access external services (databases, APIs, design tools).

## P

**Phase**
A step in the development loop (Explore, Plan, Implement, Verify, Review, Document, Deliver) or a workflow (Investigate, Fix, Submit).

**Port**
An abstract interface in the architecture. Ports define what's needed; adapters provide it. Example: `design-visual` is a port; `design-color` is an adapter.

**Product Instance**
Product-specific source of truth under `products/<product-id>/`. Contains product-specific workflows, rules, and configuration.

**Profile**
A Hermes-specific concept — an isolated configuration space with its own skills, memories, and cron jobs. Example: `ai-native-engineering` profile, `arbiter` profile.

## Q

**Quality Gate**
See Gate.

## R

**Rules Layer** (Layer 5)
Architecture layer defining constraints agents must obey. Examples: DDD rules, clean architecture rules, API rules, security rules.

**Runtime**
An execution surface for agents. Examples: Hermes Agent, Claude Code, OpenAI Codex, Cursor AI, CI/CD.

**Runtime Contract**
A contract governing runtime infrastructure (not skills or workflows). Lives in `contracts/runtime/`. Examples: `agents-md`, `development-loop`, `core-source`.

## S

**Shortcut**
A declared exemption from the full development loop for low-risk work. Must be explicit — agents cannot silently skip phases.

**Skill**
Repeatable execution procedure stored as a SKILL.md file. Atomic capability with defined inputs, outputs, and quality gates.

**Skill Adapter**
A skill that extends a base public skill with product-specific overrides. Uses `extends` field and `type: skill-adapter`.

**Skill Contract**
YAML specification in `contracts/skills/<category>/` defining what a skill must cover: capability, roles, inputs, outputs, quality gates, adapter requirements.

**Skills Layer** (Layer 6)
Architecture layer defining repeatable execution procedures.

**SOP (Standard Operating Procedure)**
Operational procedure for recurring tasks (deploy checklist, incident playbook). Different from workflows (development processes).

## T

**Tool/MCP Layer** (Layer 8)
Architecture layer defining external capabilities and access policies. Tools should be registered with purpose, allowed agents, risk level, required approval.

**Transition**
An allowed move between development loop phases. Some transitions are conditional (e.g., Verify → Implement only on failure).

## V

**Verification**
Proving changes work with real tool output. "I believe the tests will pass" is not verification. Running `npm test` and showing the output is.

**Version Pinning**
Adapter skills pin to a contract version using semver ranges: `^x.y.z` (major-compatible) or `~x.y` (minor-compatible). Prevents silent drift.

## W

**Workflow**
A sequenced process that composes skills. Lives in `contracts/workflows/`. Examples: bugfix, code-review, deployment, new-feature.

**Workflow Contract**
YAML specification defining required phases, quality gates, and skill dependencies for a workflow. Abstract — teams implement their own branch strategy and tooling.
